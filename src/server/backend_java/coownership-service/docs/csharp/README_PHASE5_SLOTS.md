# Фаза 5: слоты периода и их состояние

## Назначение
Эта фаза не является отдельным Kafka- или gRPC-контрактом. В текущей версии сервиса отдельной доменной операции переназначения слотов нет; слоты создаются, назначаются при формировании периода и далее используются для booking / settlement.

С точки зрения интеграции C# это внутреннее состояние доменной модели, а не внешний endpoint. Если позже появится отдельный сценарий переназначения, для него потребуется отдельный контракт и отдельные тесты.

## Что ожидает сервис на входе
В текущей реализации внешний вход отсутствует. Для понимания модели данных важно знать, что:

- `periodId` — UUID периода.
- `OwnershipSlot` хранит `date`, `ownerId`, `status`, `isOverride`.
- Слоты текущего периода создаются при переходе листинга в `FILLED`.

Если в будущем появится API переназначения, оно должно будет работать только с датами внутри периода и только со слотами в допустимом статусе.

## Бизнес-ограничения
1. Период должен существовать, иначе это внутренний `NOT_FOUND`-сценарий доменной модели.
2. Слоты периода не должны использоваться после перевода периода в `SETTLED`.
3. Для booking и settlement важны только реальные слоты периода на конкретные даты.
4. Даты вне периода не должны попадать в расчёт дохода.

## Что именно меняется
Для слотов периода в текущей версии меняется только их статус в процессе обработки booking:

- при подтверждении бронирования затронутые слоты помечаются `BOOKED`;
- при создании следующего периода новые слоты формируются заново на основе шаблона долей;
- при settlement слоты не переписываются, а только участвуют в расчёте.

После успешного обновления слоты сохраняются одним `saveAll(...)`.

## Побочные эффекты
После операций со слотами сервис пишет в outbox связанные с фазами 3 и 6 события:

- `COOWNERSHIP_FILLED_OUT`
- `PERIOD_SETTLEMENT_READY`

Они содержат payload, описывающий создание периода или готовность settlement.

```json
{
  "periodId": "3f1a2b4c-5d6e-7f80-1234-abcdef012345",
  "startDate": "2026-04-01",
  "endDate": "2026-04-30"
}
```

Сами `OwnershipSlot` не публикуются как отдельный contract для C#.

## Что не меняется
- `templateDaysMask` используется только как шаблон для следующего периода.
- Статус периода переводится в `SETTLED` только на фазе settlement.
- Отдельный внешний endpoint для переназначения слотов в текущей версии отсутствует.

## Что важно C# стороне
1. Это не Kafka и не gRPC-контракт, а внутреннее состояние доменной модели.
2. Следите за тем, чтобы booking не затрагивал даты вне периода.
3. Не ожидайте отдельного event'а на переназначение слотов в текущей версии.
4. Для интеграции с периодом ориентируйтесь на `COOWNERSHIP_FILLED_OUT` и `PERIOD_SETTLEMENT_READY`.
5. Если позже появится API переназначения, его контракт будет оформлен отдельно.

## Тесты
Сейчас отдельного публичного RPC или Kafka-контракта для переназначения слотов нет. При изменении логики стоит добавлять отдельные unit-тесты на реальные сценарии `applyBookingConfirmed(...)`, `triggerFilledOut(...)` и settlement.
